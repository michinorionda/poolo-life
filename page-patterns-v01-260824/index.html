Page Patterns — A / B / C

告知ページの型を、
3つに分ける。

POOLOの告知ページは、いまひとつの型で作っています。写真ドリブンのヒーロー → 日付帯 → 要点 → 導入 → 流れ → 問い → 声 → FAQ → CTA。この型は完成度が高い一方で、回の性質に関係なく同じ形になるという問題を抱えています。90分の無料ワークショップも、1泊2日の現地プログラムも、写真が1枚もない新企画も、同じ骨格で作ることになる。

そこで、型を3つに分けました。3案とも poolo-ds のトークンとコンポーネントを参照していて、ブランドの色・書体・ヘアラインは一切変えていません。振っているのは、レイアウト・写真の使い方・情報の密度・余白の取り方だけです。

比較のため、3案とも中身はまったく同じにしてあります（サンプル：架空日程の90分ワークショップ）。差はすべて型の差です。

01

回の性質で、型を選ぶ

こういう回選ぶ型理由
90分の無料ワークショップ（毎週の量産）A｜Standard読み手は数秒で「行けるか」を判断する。日付・場所・定員・参加費が1画面目に入っていることが最優先。作る側の工数も最小。
写真が用意できない新企画・初回開催B｜Editorial写真の穴を余白と組版で埋める。明朝の大見出しと罫線だけでファーストビューを成立させる型。
長い思想を読ませたい回B｜Editorial本文が主役。1行の文字数と行間を読み物として設計してあるので、長文でも疲れない。
現地開催・合宿・旅のプログラムC｜Immersiveその場の空気ごと伝える必要がある回。写真の面積を最大化し、密度を落として「めくらせる」。
有料・高単価で、判断に時間がかかる回C｜Immersive世界観で惹きつけたうえで、事実（日程・費用）を明快に置く。鞆の浦のLPはこの型に近い作りです。
複数回の講座・ゼミ（日程表が主役）A＋日程一覧型Aをベースに .date-list と .apply-steps を足す。既存のゼミページがこの形です。
02

密度の差を、実測する

「密度が高い／低い」を感覚で語らないよう、実際に測りました。画面幅1440×900pxで、ページ上端から各要素までの距離とページ全体の高さです。ヘッダーが64pxあるので、836px以内なら1画面目に入ると考えてください。

＊現行の型だけは掲載内容が少し違います（お知らせバンドと写真ブレイクが1枚多い）。全高の比較は参考値として見てください。型A・B・Cの3つは中身が完全に同じなので、数値の差はそのまま型の差です。

A Standard／要点先行For weekly workshops 単体で開く ↗
狙い
短時間・無料・先着の回を、最小工数で量産する型。ヒーローの上下余白と写真の高さを詰め、日付帯（606px）と要点4セル（735px）をファーストビューの中に引き上げた。セクション間の余白も詰め、お知らせバンドと写真ブレイク1枚を落として、写真はヒーロー＋ブレイクの計2枚で成立する設計にしている。
向いている回
90分のワークショップ、オンライン開催、写真が2枚しかない回、毎週の量産。判断材料が早く出るほど申込につながる回。
向かない回
合宿・宿泊など情緒で惹きつける必要がある回。密度が高いぶん、余韻は残りにくい。
B Editorial／読ませるNo photos needed 単体で開く ↗
狙い
写真がなくても成立させる型。ヒーローに写真を置かず、明朝の大見出し（最大80px）・罫線・家紋だけでファーストビューを組む。導入は本文カラム＋右の傍注カラムの2段構成で、傍注を丸ごと外してもレイアウトが崩れない。「そんなとき、ふと。」のような転換の一言を上下罫つきの大引用として独立させ、ページのリズムを引用でつくる。
向いている回
新企画・初回開催で写真がない回。オンラインのみの回。思想やコンセプトを長めに読ませたい回。急ぎで出したい回（写真の手配が要らない）。
向かない回
会場や土地の魅力が申込理由になる回。文字量が多いぶん、流し読みでは伝わりにくい。
C Immersive／写真主導For real places 単体で開く ↗
狙い
その場の空気ごと伝える型。白い面に置いたことばから始まり、そのまま全幅の写真へ流れ込む。写真ブレイクを3回はさみ、ページのリズムを写真がつくる。1画面に1メッセージ。3つの型でいちばん密度が低く、全高は型Aの1.5倍になる。
向いている回
現地開催・合宿・旅のプログラム。有料で、判断に時間がかかる回。会場そのものが魅力になる回。
向かない回
いい写真がない回（この型は写真の質がそのままページの質になる）。ページが長くなるため、毎週の量産には重い。

提案：1つを選ぶのではなく、3つを使い分けるセットとして持つ。

この3案は「どれかを選んで残り2つを捨てる」ものではありません。回の性質が違えば、最適な型も違う——それがこの比較でいちばん確かめたかったことです。3つとも poolo-ds の上に乗っているので、併存させても運用は破綻しません。

そのうえで、量産のデフォルトは型Aにするのを推します。POOLOがいちばん多く作るのは90分のワークショップ告知で、そこでは「日付・場所・定員・参加費が1画面目に入っていること」が申込率に直結します。型Bと型Cは、条件が揃ったときに指名で使う型として持っておく——という位置づけです。

採用するなら、次のステップは3つの型を poolo-ds 側に登録することです。型ごとの骨格（どのコンポーネントをどの順に置くか）をREADMEに書き、カタログにも型見本を足せば、次回から「今回は型Bで」と指定するだけで作れるようになります。

03

採用後にやること

  • 使う型を決める（3つ全部か、絞るか）
  • 型ごとの骨格を poolo-ds/README.md に追記する（どのコンポーネントをどの順に置くか）
  • 各型で共通して使った固有CSSのうち、汎用性のあるものを components.css に還元する
  • カタログ（poolo-ds/index.html）に型見本へのリンクを足す
  • BRAND.md の「ページ構成の型」を、1つの型から3つの型の使い分けに書き換える
  • 次の告知ページを、決めた型で1本作ってみる（型が実運用に耐えるかの検証）
